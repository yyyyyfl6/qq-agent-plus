## v0.8.4 —— 表情收藏判定标准可配置（PR #31）、更新门禁不再依赖机器的 docker 访问

发布日期：2026-10-10 14:18:30 UTC

## 本次改动

这一版包含两项内容。**表情收藏的判定标准改为可配置**（社区贡献 PR #31）：该标准此前写死在
代码里，调整只能改源码，而升级会整树替换 `src/`、本地改动一次即失；现在留空即内置默认
（与之前逐字相同），填入自己的标准即生效。另一项是**更新门禁的第二处环境依赖修复**：在
"管理员已在 docker 组、但 systemd 用户管理器未继承该组"的机器上，门禁中的 3 条巡检用例
必然失败、**更新本体被直接拦死**（Issue #30 评论实测复现）—— 修复后这类机器无需先处理
docker 组即可升级本体。

## 表情收藏的判定标准可配置（PR #31，贡献者 muhan5102）

**背景**：表情自动收藏与聊天里的 `collect_sticker` 共用一段判定提示词（"以后聊天时用得上
吗"），标准写死；不同部署的取向不同（有的希望以 ACG／干净卡通为主，技术群可能相反），想调
只能改源码 —— 升级时 `src/` 被整树替换（`rsync --delete`），本地改动一次即失。

**改动**：新增可选配置 `sticker.collectCriteria`（`config.json` 的 `sticker` 段，字符串，
默认空）：

- **留空 = 内置默认，默认文案与改动前逐字相同**（老配置一字不改照旧运行）；
- 只写"收什么 / 不收什么"，身份那句（你是「谁」、正在看谁的图）仍由代码补充在前；
- 运行期读取，改完即时生效、不用重启；自动收藏与主动收藏共用同一份标准；
- 超长截断到 2000 字（判定是一次 `maxTokens: 600` 的小调用，防止请求被撑爆）；
- `collect_sticker` 被拒时给模型看的理由不再复述默认标准（避免与自定义标准相互矛盾）。

## 修复：更新门禁不再依赖机器的 docker 访问

**现象**：在"管理员已加入 docker 组、但 systemd 用户管理器未重建（因而未继承 docker 组）"
的机器上，更新协议端会报权限错误（Issue #30 原报告）；此外这类机器**更新本体也会被门禁
拒绝** —— 实测：升级到 v0.8.3 仍失败，重启用户管理器之后才通过（Issue #30 评论）。

**根因**：`test/ops-health.test.mjs` 中有 3 条断言"全绿 / healthy"的巡检用例直连真实
`/var/run/docker.sock`。更新器的部署前门禁运行在加固 unit 里：该单元未继承 docker 组时
套接字必然不可访问，而 `sudo -n docker` 回退又必被 `NoNewPrivileges` 挡死 —— 3 条用例
必然失败、门禁拒绝升级。CI 与开发机的测试进程都在 docker 组中，这条机器环境依赖一直不可见
（与 v0.8.2 的 NoNewPrivileges 事故同族：门禁用例不应依赖运行机器的环境）。

**改动**：

- 该测试文件统一把 `DOCKER_HOST` 指向自建的可读假套接字，与机器环境解耦；真实失败路径
  （不可访问 → 报红）仍由专用用例（000 权限套接字 + 注入 NNP 状态）确定性覆盖；"sudo 回退
  可用 → 报绿"那一支新增可注入的 `sudoDockerProbe` 并补确定性用例。
- CI 与发布闸门的"按 unit 的加固环境复跑"新增**"无 docker 访问"维度**（000 权限假套接字
  + `DOCKER_HOST`），此类环境依赖从此无法通过发布闸门。

## 升级影响

- **没有破坏性变更，不需要修改任何配置**。
- 表情收藏：不配置 `sticker.collectCriteria` 时行为与本版之前完全一致；自定义标准的写法见
  [docs/CONFIG-EXAMPLES.md](docs/CONFIG-EXAMPLES.md)。
- 曾受"更新装不上"影响的部署（用户管理器缺 docker 组的机器）：**自本版起，更新本体不再
  需要 docker 组**，可直接升级；更新**协议端**仍需要 docker 权限（处理步骤见 Issue #30）。

安装与部署见 [docs/OPS.md](docs/OPS.md)。

## v0.8.3 —— 修复「更新装不上」（v0.8.2 门禁在加固单元里必败）、报错可读性、提醒归属与称呼统一

发布日期：2026-10-10 03:34:50 UTC

## 本次改动

这一版首先修复一个发布级缺陷：**v0.8.2 的更新门禁在标准部署里必然失败，导致所有标准部署
（含我们自己的服务器）都装不上新版本** —— 控制台点「更新」与定时检查的失败根因同此；同时把
更新失败的报错改为直接列出失败用例（此前那段"全是群游戏测试名"的报错就是这里来的），并落地
两条群友反馈的改进：提醒归属（不再把别人托的提醒说成被提醒人自己设的）与称呼统一（按 QQ 的
备注/代号在聊天记录、成员列表、提示词里保持一个口径）。

## 修复：v0.8.2 的更新门禁在加固单元里必败（发布级）

**现象**：控制台点「更新」或定时检查 → 门禁拒绝部署 → 装在 v0.8.1/v0.8.2 的机器全部装不上
新版本（Issue #30 报告者与群友反馈的"升级失败"同一根因）。失败还会触发"自动更新自停 +
私聊通知 + 巡检报红"，而通知里嵌的错误信息整段是群游戏测试名 —— 那是**报错信息的组装
方式**造成的：更新器此前截取测试输出**结尾 2000 字符**，而测试文件按名字排序收尾时最后正好
是狼人杀/卧底这类文件，真正的失败（两条 snowluma 用例）在三百条之前，一条也看不到。

**根因**：v0.8.2 里两条 `sudo -n docker` 回退用例在构造更新器时**没有注入** NoNewPrivileges
探测，落到了真实的 `/proc/self/status`；而门禁本身就跑在带 `NoNewPrivileges=true` 的
systemd 单元里（标准部署默认如此加固）。加固环境下程序会正确地"一次 sudo 都不试"并给出
加固提示，与用例的断言相矛盾 —— 于是门禁必然失败。CI 与普通命令行没有 NNP，因此发布前
一路绿灯。

**改动**：

- 两条用例改为**显式注入**环境（默认未加固；加固路径由专门用例覆盖）；CI 与发布闸门各新增
  一步"**更新器门禁全清单**（`umask 0077` + `setpriv --no-new-privs` 复跑 unit + local +
  四个回归 harness + scan）"，把"只在门禁环境里才失败"的问题挡在发布之前。
- 失败信息组装改为 `failureDetail()`：有失败项就列出**用例名 + 断言原因 + 汇总**（含
  `describe()` 内的缩进形态与块形式诊断），找不到才退回旧口径。
- 顺带纠正一处部署记录口径：手工 tar 部署须把版本 SHA 写进**数据目录**的
  `deployed-revision`（写进应用树里的那份无效，会导致更新器一直误判"落后"、每次检查都
  真跑一遍完整更新管线然后失败）。

**升级后的建议操作**：更新到 v0.8.3 后「更新」按钮与定时检查即恢复正常；若按钮仍报旧错，
按控制台提示重跑一次部署脚本即可。

## 提醒归属：谁提的、提醒谁

**现象**：a 说"12 点提醒 b 去吃饭"，到点机器人却说成"b 自己设的提醒"。

**根因**：提醒不记归属（旧字段存的是机器人自己的名字、从未使用）；派发时整条内容被套进
"你之前给自己留过话"（那是"自安排唤醒"的框架），且只有"有人让你"没有名字 —— 模型只能
自己圆，圆出了错误归属。

**改动**：`remind` 支持 `to`（提醒谁）/ `from`（谁请你提醒的；必须能在本轮消息里对上人，
对不上就不记 —— 防"就说是管理员让提醒的"这类借名与猜错）；到点话术带上归属（"彭于晏 之前
让你在 12:00 提醒吴彦祖：去吃饭"），没有归属时明确写"别猜、也不要说是被提醒的人自己设的"；
定时提醒的唤醒改走逐字分支、不再自称"管理员从控制台唤醒"。控制台 → 设置 → 定时提醒，
列表每行显示"谁请你提醒谁"。

## 称呼统一：按 QQ 的备注/代号

**现象**："我让 bot 以后叫他 pyy"，机器人有时喊 pyy、有时喊群名片。

**改动**：备注（称呼/代号）本就存在（控制台「人物记忆页 → 备注」），这一版把它做成**全局
一个口径**：聊天记录、成员列表、消息详情、成员提示与提示词都走同一个"备注优先"；并在群里
直接可记 —— 群友让机器人"以后叫他 X"时，用新工具 `set_member_note` 落一条（只给当前会话
出现过的人设，号码编错会被拒）；`set_remark`（QQ 客户端备注）的说明改为指向它。控制台
人物记忆页的标题改为「备注（称呼/代号）」，并注明与聊天侧是同一份数据。

## 升级影响

- **没有破坏性变更，不需要修改任何配置**。
- **曾受更新门禁影响的部署**：更新到 v0.8.3 后恢复（门禁校验的是**新版本**的测试，v0.8.3 的
  测试已确定性通过）。
- 若曾手工 tar 部署过：`deployed-revision` 的权威位置是数据目录（`QQ_AGENT_DATA_DIR`）；
  写错位置不影响运行，只会让更新器误判版本，按 docs/OPS.md 的口径写对即可。

安装与部署见 [docs/OPS.md](docs/OPS.md)。

## v0.8.2 —— 控制台更新协议端修复（Issue #30）、协议端随版本对齐、值班台视觉身份

发布日期：2026-10-09 13:28:04 UTC

## 本次改动

这一版修复 Issue #30「控制台更新协议端报 docker 权限不足」，覆盖从根因定位、部署脚本自愈到
提示文案的完整链路；新增**协议端随智能体版本对齐** —— 发版触及协议端基线时，更新本体即顺带
升级，默认开启；控制台立起「值班台」视觉身份（一页两级表面与细线、设计标度收口、材质轴五档
与边缘折射）；并收口一批安全与稳定性问题（工具 URL 直通协议端形成的 SSRF、上游响应缺少字节
上限、`send_group_file` 可读取本机文件外发、`docker compose pull` 期间主进程事件循环被阻塞、
台账保留期清理长期未执行）。

## Issue #30：控制台「更新协议端」报 docker 权限不足

**现象**：控制台点击「更新协议端」报
`permission denied while trying to connect to the Docker daemon socket`，而同一账号在交互
shell 中可正常使用 `docker`。

**根因**：问题不在 `docker.sock` 的权限配置，而是运行控制台的进程没有 `docker` 组。控制台以
systemd 用户服务运行，其补充组在 user manager 启动时即被固定（启用 linger 的机器上即开机
时）；后续执行 `usermod -aG docker` 仅影响新建的 shell，长期运行的 manager 不会随之更新。
实测非 root 进程无法为自身补充缺失的组，因此不存在"进程内自愈"的方案。

**改动**：
- **部署脚本自愈**：`deploy.sh` / `deploy-all.sh` 在收尾阶段检查部署用户的 docker 组身份与
  服务进程的组快照，缺项即补齐 —— 加入 docker 组，并以 `stop → sleep 3 → start` 重建 user
  manager（服务中断约 10 秒后自动恢复）。同时移除两条不可靠的修复方式：`systemctl restart
  user@`（实测触发 `status=219/CGROUP`，且失败后不会自动恢复）与 `loginctl terminate-user`
  （不会自动带回管理器）；文档、错误提示与测试均不再推荐。
- **提示与预检**：更新前的预检先探测 `docker info`（含回退路径），两条路径都不可用时才给出
  人工修复步骤；错误信息按当前机器的实际状态生成可直接执行的命令。
- **运行时回退（仅限未启用加固的部署）**：直连遇到套接字权限错误时，回退以 `sudo -n docker`
  执行（非交互、仅一次；无免密 sudo 时立即失败，不会挂起）。标准 unit 默认带
  `NoNewPrivileges=true`，加固部署下该回退不生效，程序会如实报告原因；可用
  `QQ_AGENT_NO_SUDO_DOCKER=1` 关闭。
- **修正一处永不失效的误报**：健康检查此前以巡检进程自身的 sudo 结果为判据，在加固部署下会
  长期显示正常；现改为读取主进程的 NNP 状态，并新增 `docker-socket` 巡检项。
- **代价说明**（docs/LINUX.md）：将账号加入 docker 组等价于授予其 root 权限（可挂载宿主文件
  系统）；文档列出三条处置路径（接受 / 关闭控制台更新并移除组 / 将 `server.host` 收回
  127.0.0.1）。

**升级后的建议操作**：更新到 v0.8.2 后重跑一次部署脚本（`deploy.sh` / `deploy-all.sh`），
或按控制台给出的命令执行；完成后「更新协议端」即可正常使用。

## 协议端随智能体版本对齐（新功能，默认开启）

协议端基线（镜像版本）是代码常量，只随本体新版本到达用户机器；"部署新版本后主服务携带新代码
重启"是机器上出现新基线的唯一时机，此前该时机不做任何事 —— 导致"能力已具备、协议端版本过旧"
（例如贴纸显示成图片）只能由用户自行升级协议端。现在：

- **发版触及协议端基线时，更新本体即顺带完成对齐；基线未变时不产生任何动作**（基线未变时
  `outdated` 为假，自然成为 no-op）。对齐复用更新器的完整流程：修改 `.env` → `pull` →
  `up` → 等待 WebUI 就绪 → 失败自动回滚；数据卷不动、登录态保留。
- 自定义镜像（`autoUpdate.snowluma.image`）始终优先，锁定版本的机器不会被自动变更；设置页
  OneBot 分区新增「随智能体版本对齐协议端」开关（默认勾选）。
- 对齐失败仅记录日志，不影响本体更新自身的结果。

**配套**：更新器由同步执行改为**异步执行** —— 此前 `docker compose pull`（超时 300 秒）期间
整个主进程事件循环被阻塞（消息不处理、控制台无响应、健康探测失败），而手动 / 周期 / 随版本
对齐三条路径共用该执行器，本功能默认开启后会常态触发。

## 控制台：值班台视觉身份

- **一页两级表面**：KPI 行作为**一整块**表面呈现（格与格之间为 1px 发丝线），展开面板改为
  **细线分节**（不再逐块成卡）；玻璃材质施加于整行，而非逐格。
- **设计标度收口**：323 处字号与 139 处圆角（含 JS 内联样式）全部改用 token；同时清理
  `[data-theme='dark']` 中已被 `:root` 覆盖的圆角死声明（此类声明表现为"修改不生效"）。
- **`--voice`（黄铜）**：全站唯一暖色，只用于标识机器人自己发出的内容 —— 「已发言」徽章、
  上下文中 assistant 回合、归档表中机器人发送的消息、总览页「机器人」卡片。
- **材质轴（第 8 轴）**：实心 / 磨砂 / 液态玻璃 / 亚克力 / 描边五档；另有实验性的**边缘折射**
  （默认关闭，按每个表面的实际尺寸计算位移场、仅边缘弯折；不支持的环境自动不生效）。
- **动效收口**：折叠面板展开与收起均走高度过渡；列表行退场先量后写（删除 N 行不再触发 N 次
  强制重排）、行重新出现时取消退场；KPI 数字计数在数值未变时不滚动；悬浮位移统一限定在
  `(hover:hover)` 与 `(pointer:fine)` 环境。另修复用量页「展开全部」按钮此前未绑定事件的
  问题（模型超过 20 个时无法看全）。

## 安全与稳定性收口

- **工具 URL 直通协议端形成 SSRF**（`send_group_file` / `set_my_avatar` / `read_image_text` /
  `upload_to_group_album`）：模型给出的地址被原样交给协议端请求，该请求发生在程序网络层之外、
  `safe-fetch` 无法覆盖；提示词注入配合内网地址即构成 SSRF 与外带通道。现已新增公网地址
  校验，并在上述 4 处接入。
- **`send_group_file` 拒绝非 http 地址**：非 http 前缀（`file://…`、`/app/data/...`）会被
  协议端按本机路径读取并以群文件发送；本机内容改由 base64 通道传递。
- **上游响应全面收口为有界读取**：18 处"先整体读入再判断长度"（长度上限实际无效）改为边读
  边截断、按用途分档上限；`safe-fetch` 的截断标记改由读取路径如实给出。
- **租约回收与在跑执行冲突导致重复回复**：现在会排除本进程仍在运行的租约，同一批消息不会被
  回答两遍。
- **台账保留期清理此前"在线等于未执行"**：三本台账的清理挂在进程启动时（连续运行数周的实例
  上从不触发），改为进程内每日闸门；runs 台账也纳入控制台每日清理。

## v0.8.0 —— 群名片工具、16 轮全项目复审与生图发送修复

发布日期：2026-10-07 03:36:05 UTC

## 本次改动

这一版的主体有两件事。其一，机器人现在可以修改自己在群里的群名片——社区贡献（@foxlesbiao，PR #19）。其二，修复了生图发送「时好时坏」的根因：协议端的 HTTP 通道对请求体有 ≈2MiB 上限，大图的 base64 传输会被掐断（真实用户报告，Issue #21）。此外是第十六轮全项目复审的集中收口（11 P2 + 8 P3），以及此前数轮复审的零散修复。

## 生图发送「时好时坏」的根因：协议端 HTTP 请求体上限（Issue #21）

**现象**：生成贴纸发送时好时坏——小图偶尔能发出去，大图必失败；异常面板里只有一条 `fetch failed`，没有任何可定位的信息。
**根因**：SnowLuma 的 OneBot HTTP 端点对请求体有 ≈2MiB 的硬上限，超过时在 100-Continue 之后直接掐断连接（实测：2MB 通过、2.5MB 掐断）。而生图发送的链路是把整张图 base64 后塞进消息段，1024×1024 的图 base64 后通常 2~3MB+，正好压线：图小碰巧成功、图大必挂。文字消息只有几十字节、旧表情发送的是 QQ CDN 链接，都不经过这条上限，所以此前只有生图受影响。看不见真因是第二个问题：undici 的外层报错恒为 `fetch failed`，真正的 ECONNRESET 嵌在 `error.cause` 里，落库时被丢掉了。
**改动**：请求体超过 1.5MiB 的 OneBot 调用自动改走 WebSocket 通道（事件常驻连接，实测 3MB 无恙）；结算口径与 HTTP 通道一致——协议端明确拒绝报失败可重试，断线与超时按「结果未知」处理，不会把没把握的失败降级成静默重发。WS 未连接时回落 HTTP，行为与此前一致。同时异常落库会解出 `error.cause` 链（最多 3 层、逐层脱敏），以后这类网络异常在面板上直接显示「真因: ECONNRESET …」。

## 群名片工具 set_group_card（社区贡献）

**现象**：此前机器人无法修改自己在群里的群名片。
**改动**：新增 `set_group_card` 工具，模型可在被要求时修改机器人在群里的群名片（@foxlesbiao，PR #19）。合并后补了两处：送达后记账走统一兜底路径、取消信号全链透传。

## 控制台 server 整节替换的令牌清空窗口

**现象**：持有控制台令牌的人提交整节替换配置的请求可清空令牌——运行中的实例不随配置重绑套接字，原本「令牌 + 仅本机可达」的保护会静默降级为免鉴权。
**根因**：此前的加固只覆盖了「重启后拒绝以无令牌启动」的路径，漏掉了运行期窗口；且「本机判定」原先看可伪造的 Host 头。
**改动**：本机判定改看 TCP 对端地址；实例仍绑在非回环地址时，拒绝一切会清空令牌的 server 整节替换（409），且属于预期内拒绝、不会触发异常告警。

## 会话静默卡死的一处窗口

**现象**：极小概率下，某个会话此后不再响应任何消息（被 @、被唤醒、恢复循环全部绕开），直到重启。
**根因**：唤醒流程里「登记为运行中」与主逻辑之间的同步准备段（读线程、会话落盘、事件监听）一旦抛错，收尾代码不执行，运行中标记永远不被清掉。
**改动**：准备段单独兜底，出错时清理控制器、定时器与租约，会话落 error 终态后原样上抛，不再留卡死窗口。

## 认不出自己：登录信息获取失败无重试

**现象**：协议端重启等竞态下，机器人可能认不出自己的消息与被 @ 的判定；严重时对指令整体无响应。
**根因**：获取自身账号信息只在连接建立时调用一次且没有重试，失败一次留下的空值会一直生效。
**改动**：退避重试 + 60 秒兜底循环，并在相关判定处加双守卫。

## 网关返回畸形工具调用时的整批失败

**现象**：部分网关或自部署推理服务返回缺少 id 的工具调用时，下一轮请求被端点整体拒绝且不可重试，当前对话批次转人工、被 @ 的消息无人回。
**根因**：原生工具调用链路假定 id 一定存在，缺 id 的消息进不了标准格式。
**改动**：进消息列表前补全 id 与类型、参数字符串化，与文本兜底链路口径一致。

- 未读扫描窗口与批处理量统一，被 @ 的判定不再漏看较长的未读队列。

## v0.7.8

发布日期：2026-10-04 03:49:58 UTC

## 本次改动

这一版的主体是控制台的一项日常操作：切换语音回复、语音转写、图片生成的服务预设时，已填过的 API Key 随服务一起切换，不再需要逐家重新获取并填写。围绕该功能建立的凭据记忆机制在四轮发布前审查中修正了 20 处缺陷，其中 4 处为加固过程引入的回归。

## 切换服务预设时 API Key 跟随切换

**现象**：切换服务预设后 Key 输入框变为空白；重新填写后，先前那家服务的 Key 被覆盖，切换回去时无法取回，只能重新获取。
**根因**：三类凭据此前只存单槽，任何一次填写都会覆盖上一次的值，服务之间没有各自的存储位置。
**改动**：三类凭据改为按槽位记忆——语音回复按服务标识、图片生成按主机名、语音转写按「服务 + 主机名」（转写含 `apiKey` / `secretId` / `secretKey` 三种）。映射由服务端独占写入，客户端提交的同名字段在保存前丢弃。每把凭据同时记录归属标记（`tts.apiKeyService`、`imageGen.apiKeyHost`、`asr.apiKeyProvider` + `asr.apiKeyHost`），运行期仅发送归属匹配的那一把——将 A 家的 Key 发往 B 家不会报错，只会在对方后台留下一条 401 或一笔异常计费，因此该约束为强制校验。切换离开时，当前凭据先归档至其所属槽位再置空（存量实例的 Key 仅存在于单一字段，直接置空即永久丢失）；控制台「显示」按钮按当前选中项回读，不再回显其他服务的明文。

## 语音回复单槽 Key 在「切换服务并填写新 Key」时丢失

**现象**：存量实例中，切换服务并填写一把新 Key 后，再切回原服务且不填 Key 时，原 Key 已不可用，且无法从任何位置取回。
**根因**：归档逻辑原先只位于「未填写新 Key」的分支内，「切换服务并填写新 Key」这一常用路径完全绕过归档——旧 Key 留在单槽，归属标记却已指向新服务；此后切回原服务时，归属比较判定为「他家的」，而归档位置已被新 Key 占用，于是跳过归档并直接置空。
**改动**：归档提至两个分支之前无条件执行，与图片生成、语音转写保持同一口径；填写新 Key 的分支同时将单槽替换为新值，保证「单槽所载」与「归属标记所指」始终为同一把。

## 语音转写归档槽缺少类型守卫

**现象**：`asr.keys` 中被手工改为标量的槽位（`{"tencent":"SCALAR"}`）会在保存时被展开为 `{0:'S',1:'C',…}` 形式的字符索引键并写入 `config.json`。
**根因**：同一段代码中目标槽位已设「条目必须为对象」的守卫，归档槽位未设，属遗漏。
**改动**：两处共用同一个 `entryOf()`；`migrateConfig` 补充条目级归一，覆盖读盘路径。

## 异常日志筛选与人物印象搜索无响应

**现象**：异常处理页的状态与等级筛选选定后表格不刷新；人物印象页搜索框按回车无响应。用户表现为筛选时灵时不灵，而异常日志页在此期间将未筛选的行作为筛选结果呈现。
**根因**：整块重画前设有「焦点位于输入控件时暂不写入」的守卫，用以避免后台轮询覆盖正在输入的内容，但该守卫无法区分「后台轮询触发的重画」与「该控件自身触发的重画」。
**改动**：新增 `options.force` 通道，由用户主动触发的刷新显式传入，后台轮询仍受原守卫保护；重画后将焦点归还至同一控件，光标置于末尾。

## 服务端纠正后的值被未保存的输入覆盖

**现象**：好友管理页将 `99999` 填入上限为 `365` 的输入框，服务端存储 365，界面重画后仍显示 99999，即存储值与显示值不一致。
**根因**：「保留未保存输入」仅判断「用户是否修改过该控件」，未判断「服务端本轮是否也修改了该值」。
**改动**：两个条件同时成立时才回填，服务端修改过的字段一律以服务端为准。同处一并修正同名控件更换类型、下拉选项消失时不强塞非法值的情形。

## 凭据与配置的边界

- `migrateConfig` 不再为归属未知的图片生成 Key 补记归属。合并路径补记等同于将其绑定到本次保存刚修改的地址，用户切回原地址时校验不通过，凭据被锁定；读盘阶段仍照常补记（移入 `loadConfig`），升级中的实例不受影响。
- `asr.providerDefaulted` 改为在整节替换的有效体上删除。节点层的 `delete` 在 `__replace__` 下不作用于最终配置，替换体中的同名字段会落盘并永久屏蔽 `ASR_API_KEY` 环境变量。
- 配置段被提交为标量或数组时按「该段未修改」处理，不再导致整个 `/api/config` 返回 500。

## 其余修复

- 滑条回填服务端实际存储值后补发 `input` 事件：程序化写入 `.value` 不触发该事件，导致滑块读数与填充色停留于旧值。
- 语音转写配额在下载、转码、超时失败时退还。
- 模型重试耗尽后不再重复投递；响应为空时明确报错，不再静默返回。
- 当日预算耗尽的提示改为每个会话每天仅提示一次，主动发言路径不再重复播报。
- 记忆查询补充返回条数上限，并按最近观测时间排序。
- 贴纸收藏的 `collect` 在失败时退还计数。
- `deploy.sh` 的失败路径补上真实调用点锚点：原锚点位于函数定义处，任何改动均可通过校验。
- 发布流水线新增「tag 与 `package.json` 版本号一致」校验，版本号不符时中止发布。

## 升级影响

- 部署侧无新增依赖，沿用上一版的 `npm ci` 流程即可。

## v0.7.7 —— 控制台性能、删除/保存体验与巡检判据修正

发布日期：2026-10-02 04:18:37 UTC

## 本次改动

这一版集中在控制台的响应速度与「整页重拉」体验，外加健康巡检判据的一次修正、两处依赖升级，以及发布前审查补上的一批小项。

## 控制台响应性能

**现象**：每个页面打开都要等几秒，用量页更久；贴纸列表里缩略图多时尤其明显。
**根因**：① JSON 响应完全不压缩；② 贴纸图片每次打开都全量重下；③ 用量统计每次都要遍历并解析全部会话文件，而 20 秒的单槽缓存在「状态栏按今天、页面按 7 天」两个区间之间来回被顶掉，几乎从不命中。
**改动**：超过 1KB 的 JSON 响应启用 gzip（按 `Accept-Encoding` 协商，压缩与不压缩两侧都发 `Vary`）；贴纸图片按本地库 / 远程地址两个分支发 `ETag` 与长缓存（本地 7 天 immutable、远程 24 小时），`If-None-Match` 命中回 304；用量统计加 mtime 预筛（早于窗口起点 6 小时的文件直接跳过）与按区间分槽的 60 秒缓存。

## 删除与保存不再整页重拉

**现象**：观测页删一张图后整页刷新、滚动位置被顶回顶部；资产编辑/新增保存后整格重渲染两次。
**根因**：服务端先广播 SSE、后回 HTTP 响应，删除/保存请求自己的回声比响应先到，触发了「清空状态 + 重拉」。
**改动**：删除改为就地摘除（本地列表摘一条 + 概览计数减一 + 直接移除卡片节点，拿不到节点才退回重渲染），SSE 的 delete 事件同样就地过滤且幂等；保存侧引入写入在途守卫（计数语义，连续保存不会互相顶掉窗口）与就地重拉并还原滚动位置；身份、记忆的保存与删除所触发的 `identity-pilot-update` 回声也纳入同一道守卫。

## 健康巡检判据修正

**现象**：安静时段与「按响应概率决定不回」被误判成收发停止，连续三次给 owner 弹私聊告警。
**根因**：旧判据是「入站新 → 出站必须新」，把合法沉默当成故障。
**改动**：判据改为「到期的入站消息有没有被处理」——停在 `pending` 且超过 60 分钟宽限的，加上**重试耗尽（`failed`）且发生在最后一次成功出站之后**的（模型网关整体打挂时消息会在十几秒内全部转 `failed`，只看 `pending` 会静默漏报）；`observe` 模式、Agent 暂停、当日预算降级三种「故意不处理」自动跳过。已知边界：发送结果待确认（`held` / outbox `sending|unknown`）的批次不在判据内，仍由控制台「待核对」流程人工兜底。

## 依赖与 CI

- `ws` 8.21.3 → 8.22.0、`undici` 6.28 → 8.11.2；undici 8 要求 Node ≥22.19，项目低限随之从 22.13 抬到 **22.19**，并新增用例钉住「运行期依赖的 engines 不得越过项目地板」。
- GitHub Actions：`actions/checkout` v7.0.1、`actions/setup-node` v7.0.0（仍按 commit SHA 钉住）。

## 升级影响

- **运行期依赖有变化：手工 `git pull` 部署需要重新执行 `npm ci`；Node 需 ≥22.19**（使用 `deploy.sh` 时其 `.runtime` 会自动安装 22.23.2，无需手工处理）。
- 健康巡检判据变化：安静时段与「按概率不回」不再误报；「消息重试耗尽且此后没有成功发出」会新增告警（这是修漏报），包括低峰时段单条消息重试耗尽的场景，约 1 小时后也会告警。
- 控制台行为变化：删图与保存不再整页刷新，滚动位置保留。

安装与部署见 [docs/OPS.md](docs/OPS.md)。

### NapCat 兼容（Issue #22）

- **现象**：运行日志里反复出现"补进 N 条（重启/断线期间漏掉的）"且计数稳定增长；协议端没有任何报错；断开事件在日志里完全不可见。
- **根因**：NapCat 的 OneBot WebSocket 服务端不回应 PING，而是直接销毁连接（客户端看到 `close code=1006`、永远收不到 pong）。客户端每 30 秒发一次 PING，连接生命周期因此被压到约 30 秒，每轮留下 3~4 秒接收盲窗。

- **升级影响**：会回 pong 的协议端（如 SnowLuma）行为与旧版一致；NapCat 用户在默认配置下自愈（启动后最多断一次，之后不再发送 PING）。

- 控制台新增：图片生成页（默认关闭）、「设置 → OneBot」的心跳与补课控件，以及若干密钥开关。

## v0.7.5

发布日期：2026-09-29 08:39:14 UTC

## 本次改动

这一版加入三款群游戏（数字炸弹 / 谁是卧底 / 狼人杀），语音回复扩到四家服务商（含豆包语音合成 2.0），并补上定时提醒的控制台页与群日报；另外修掉一批由三轮对抗性审查发现的边界问题。

### 群游戏：数字炸弹 / 谁是卧底 / 狼人杀

- **背景**：群游戏需要同时满足"隐藏信息、轮次推进、超时兜底"，而主持模型不能看到牌面（身份、词与查验结果）。真人群里还有一批模拟环境覆盖不到的情况：未参加的人在群里插话、只潜水不发言、中途退出、夜间不交行动、白天无人先开口。
- **开局方式**：需要私聊的游戏先挂一段报名（默认 45 秒，想玩的在群里回一句「我玩」），到点人数不足即取消 —— 不再把仅在群里插话的围观者拉进局，也不给他们发身份私聊。
- **真相与话术分离**：身份、词与查验结果只走私聊；模型只拿到公开摘要（存活名单、天数、公开死讯），结构上无法说出身份。引擎发给玩家的私聊在落库时即标记为 `game-secret`，提示词历史、翻页工具与消息详情等所有出口统一过滤。
- **真人群的边界**：白天以三个出口中先到者为准（固定讨论时长 / 超过半数存活玩家说「投吧」/ 全员发言完毕）；夜间行动窗口 90 秒，到点按已收到的结算；出局者在群里的发言与投票一律不计入判定（并在出局时私聊本人说明）；同一玩家反复私聊刷行动时，按"每人每夜最多 4 条回执"限制。
- **游戏期间私聊豁免**：引擎发给本局在册玩家的私聊不受 `allow.private` 白名单限制（`deny` 仍优先、仅在本局进行中生效、失败不重试、内容全部为引擎文本）。狼人杀整局依赖私聊，没有这项豁免就只有"全员加入白名单"才可进行；模型自身发送的消息仍受白名单约束。
- **狼人杀规则**：6~9 人（6 人局为 2 狼 / 1 预言家 / 1 女巫 / 2 民，7 人起加入守卫，9 人为 3 狼）。女巫持有解药与毒药各一次，一晚最多使用一瓶，不能自救；守卫与女巫同时保护同一人时该人仍然出局（同守同救必死）；狼刀确定之后才私聊询问女巫（提示中写明被刀者），此后狼方改刀会被拒绝。
- **开启方式**：控制台 → 设置 → 实验功能 → 群游戏：勾选允许的游戏、报名时长、白天讨论时长、每局人数上限、结算是否公开身份。默认关闭。

### 语音回复扩到四家服务商（含豆包语音合成 2.0）

- **背景**：此前只支持 OpenAI 兼容一家。火山 v1 的鉴权（`Bearer;<token>`）与豆包 2.0 的 v3 流式（`X-Api-Key` / `X-Api-Resource-Id`、NDJSON 分片内 base64）形态完全不同，写死一种在其余服务上必然失败。
- **改动**：新增 OpenAI 兼容、火山 v1、豆包 2.0、MiniMax 四家适配；控制台按服务商预设填写地址、Key、模型与音色（豆包内置官方 2.0 音色清单 102 条，按控制台分类分组），并支持试听。
- **附带修复**：语音与图片类发送的超时由 15 秒放宽到 60 秒 —— 实测一条 7 秒语音协议端需要 16.4 秒，原超时会把已发出的语音记为"结果未知"。

### 定时提醒与群日报

- **现象**：提醒此前只存在于内存，重启即丢；多条同时到点会叠加派发；派发前未做预检，会把尚未提醒的记录标记为"已提醒"。
- **改动**：改为落盘持久化、同一会话多条合并、派发前预检；控制台新增"定时提醒"页（启用开关、待触发与最近完成列表、单条取消），该开关同时门控 `remind` 工具与到期派发。群日报把最近 24 小时的群聊汇总发送到指定群，发送时间格式做了校验与兜底（写错不再静默不跑）。

### 审查修复

- **引擎私聊的隔离此前只做了一半**：`game-secret` 标记只打在 ingest 回显侧，而存储按 (chat_key, mid) 幂等、命中重复不回填，标记因此恒不生效 —— 模型在私聊里能看到自己的身份与查验结果。现改为发送侧落库时即标记，按 id 单查、列出可见 id 等出口一并过滤。
- **可无限刷新的三条路径**：出局者反复发「不玩了」可绕过"每人每夜 4 条"限制（实测 20 条得到 20 条回执）；投票阶段反复「投自己」每次都回一条群消息；数字炸弹的越界提示可无限刷新。三处分别按配额或"每人每阶段一次"限制。
- **重启会重复播报**：`tick` 推进的阶段不落盘（此前只在 `phase === 'ended'` 时保存），任何一次重启都会回滚一个阶段，重发"天亮了"与夜行动提示。现改为发送成功后落盘，并把存盘改为 tmp/rename 原子写。
- **退出的守卫仍然挡刀**：`pending.guard` 保存的是目标，作废时却与提交者的 uid 比较，只有"守自己"才会命中 —— 已出局玩家的行动会改变存活结果。现按角色清理。
- **其余**：同一个人在两个群各一局时，一条私聊被两局各执行一次；狼在刀口锁定前减员导致刀口永不锁定、女巫整夜收不到询问；名单未去重（模型把同一人写两遍，该玩家会拿到多张身份）；`roundSeconds` 对狼人杀是死配置、`recruitSeconds` 写 `null`/空串的语义与文档不一致；名单报错现在区分"对不上"与"被人数上限截断"。
- **升级影响**：群游戏默认关闭，不开启则不影响任何既有行为；语音与提醒的默认行为不变。

安装与部署见 [docs/OPS.md](docs/OPS.md)，逐条改动见 [docs/CHANGES.md](docs/CHANGES.md)。

- **现象**：库里有那张表情、备注也没错，`send_sticker` 仍报"找不到表情"。

- **附带**：工具失败现在也写一行 journal（原先进控制台异常面板、journal 里查不到，排查容易漏），文本走统一脱敏（与异常面板同一套规则，并补上 `access_token` / `api_key` 这类带下划线前缀的参数名）。

## 本次改动

这次的重点是**语音与视频**，另有一批控制台与发送链路的修复。

### 语音转文字（多供应商）

- **可换供应商**：本机 whisper.cpp（零 Key、离线）、火山 Seed-ASR、任意 OpenAI 兼容服务（硅基流动 / Groq / 自建），
  以及新增的四家国内云原生适配：阿里云百炼、百度短语音、腾讯云一句话识别（TC3 签名）、讯飞语音听写（签名 WSS）。

- **QQ 语音（SILK）现在能转**：QQ 的语音消息文件名写着 `.amr`、CDN 回 `content-type: audio/mp3`，实际字节是 SILK，
  而 ffmpeg 不支持 SILK（此前一律报 "Invalid data found"）。现在在本地用 WASM 解码成 16k PCM 再交给所选服务，
  不需要协议端转码。
- **视频给"画面 + 声音"两样**：画面按总时长均匀抽 4 帧拼成 2×2 帧条交给视觉模型，声音走音轨转写；
  两者独立，可以只取其一。
- **非语音音频不再被当作"人声转写"讲出去**：音乐/音效没有停顿，识别模型会据此编出像模像样的假文本
  （实测两个模型各编各的）。现在按停顿比例判据（≥3 秒且近静音 <5%）给模型一个"这段可能主要是音乐/音效"的信号，
  由它照实回应"没听到有人说话"。
- 长音频：国内四家的短语音接口单次 ≤60 秒，统一按 55 秒无损分片再拼接；按真实时长推流的供应商（本机 whisper、讯飞）
  超出一次运行时限会提前给出可照做的提示，并写明当前大约能转多少秒。每小时的转写次数上限可在控制台自行填写（1–200）。

## v0.7.1

发布日期：2026-09-25 23:30:50 UTC

**改了什么**

**主动发言：三项开关独立控制（用户反馈）**

反馈现象：关闭「冷场时按概率主动开话题」后，机器人仍会主动发送消息。

根因：主动发言由三条链路组成，此前仅"冷场开话题"读取配置开关：

- 冷场时按概率主动开话题（`proactive.enabled`）；
- 发言后无人回应时的追问（约 10 分钟后给一次机会）；
- 模型通过 `schedule_wake` 安排稍后发言。

后两条自引入起未受任何开关约束，因此关闭总开关不影响其行为。

改动：

- 控制台「设置 → 聊天设置 → 主动开话题」新增两个独立复选框，分别对应上述后两条链路（配置项 `proactive.followUpEnabled`、`proactive.selfWakeEnabled`）。
- 两项默认开启，与升级前行为一致，不改变既有部署的运行表现；需完全禁止主动发言时，三项须全部取消。
- 开关关闭后，已排入队列的唤醒同样作废，不再触发一次发言。
- 关闭自安排唤醒时，`schedule_wake` 工具与对应的提示词引导一并移除，避免模型调用一个不会生效的工具。
- `ops.js status` 输出两项开关状态。

**贴纸：清单改为"常用 + 未使用"轮换（用户反馈）**

反馈现象：收藏表情数量较多时，实际使用的始终是少数几张。

根因：系统提示中的【可用表情包】按使用次数降序截取前 10 条（函数内上限 30），且每次发送使计数递增，已使用过的贴纸长期占据名单，库内其余贴纸不会进入模型可见范围。

改动：

- 清单分为两段：一半为常用（按使用次数、备注、最近使用排序），一半为未使用或最久未使用；某张贴纸被使用后，下一张未使用的自动进入清单。
- 未使用项在清单中标注，提示词相应说明可直接使用、含义不确定时先查看图片。
- 排序仅取决于使用次数、最近使用时间、入库时间与 id，同一份库每次生成结果一致。该清单常驻系统提示且属于缓存前缀，若每次运行变化将导致输入缓存失效。
- 同步范围不变（收藏表情单次拉取 500 条），改动仅涉及注入模型的数量与选择方式。

**控制台：清单条数改为档位选择，并回填生效值**

- 「设置 → 聊天设置 → 表情包 → 系统提示里的表情清单条数」由自由输入框改为下拉档位（10 / 20 / 30 / 45 / 60）。此前输入框可填写任意数值，保存时被限制在 1~60（例如填 500 存为 60），而界面不回填，仍显示原输入值，造成实际生效值与界面显示不一致。
- 现在可选范围明确，无法填出越界值；存量配置中的自定义值（如 24）会保留为一项并选中，不会被改写。
- 保存成功后，界面回填服务端实际保存的值。

## v0.6.7 —— 响应滑条改成「数字就是概率」；被 @ 认得更准

发布日期：2026-09-22 01:17:12 UTC

这一版最大的一处改动：**响应滑条改成"上面的数字就是概率"**。

## 响应滑条：数字就是概率

以前那条滑条分四段（0-10 只回 @、10-20 加关键词、20-90 才是概率、90-100 全响应），
"只有中间那段才是概率、两头是特例"，看不懂也不好控，还有人反馈"调到中等还是都回"
—— 因为中间那段有 70% 宽，拖到正中就是 50%，本来就会回一半。

现在：

- **滑条上的数字就是概率**：拖到 30，大约每 100 批普通消息接 30 批。
- **被 @ 或命中关键词一定回**，不受这个数字影响（把关键词表清空就只回 @）。

  "普通消息 43% 概率回（大约每 100 批接 43 批）"。

老的 3 档 → 保留你原来设的概率；老的 4 档（全响应）→ 100%；每个群单独拖过的档位同样换算。

## v0.6.5 —— 修合并转发读不出来、价格与更新器的一批 bug

发布日期：2026-09-21 14:49:04 UTC

这一版没有新功能，都是修 bug。升到这一版就行。

合并转发的消息读不出来：SnowLuma 1.14.15 起，新收到的转发卡片必须拿卡片里的资源 id 去查，只给 message_id 会返回 "download forward message payload is empty"。现在收消息时直接用卡片上的资源 id，读存档里那些老转发时先 get_msg 取一次新鲜 id，两条路都不行才报错。（PR 来自 @SJMAHAHA）

远程价格表换了地址看不出来：新地址没拉通时，界面会拿新地址 + 旧数据说"已生效"。现在会写明生效的还是上一次成功拉到的那份。

价格别名里的 from / until 写成非法日期会被静默忽略，导致这个别名要么永不失效、要么回溯到全部历史，两种都会算错钱。现在解析失败就整条别名不生效。

直接在 config.json 里删掉一个渠道，它之前拉到的价目表还在按老价算钱，要重启才干净。现在保存配置或重启时就会撤销。

官方更新跑单元测试，会在服务器 /tmp 留下一堆 qq-* 临时目录。现在测试的临时目录落在工作目录里，跟着一起清掉。

好友评估、好友提议、收到的加好友请求这三张表只增不删。现在启动时清掉 90 天前已经了结的，还在等你处理的不删。

设置页有两处改动：「当前模型单价」原来和「全局兜底单价」共用同一组输入框（官方价开关打开时框里显示的是生效价、还是禁用的，很容易看错），现在拆成上面只读的「生效价」和下面可编辑的「自填单价」，框不能编辑时会写清原因；渠道倍率输入框允许填 0（0 = 这个渠道不花钱），以前填 0 会被当成 1。

人设那几条（提示词里从来没写过谁是管理员、跟着人设走的"表情策略"文案写在别的文件里、"少怼点人"只落实了一半、两张内置卡分散在两处）是 v0.6.4 修的，从更早的版本直接升上来会一起生效。

升级：控制台「控制 → 更新部署 → 立即更新」，或在服务器上跑 manage.sh update-now --confirm。更新会先跑单元测试再部署，失败自动回滚；git 通道不通的机器会自动改走 GitHub API + codeload 源码包。

## 这一版两件事

### 1. 「立即更新」多了一条下载通道（git 抽风也能更新）

## 如果你正在用 0.6.1

建议升级。另外有一件事值得顺手看一眼：如果你在 0.6.1 上点过「保存设置」，

## 修掉会算错钱的

- **包月费不再按"用过的模型数"翻倍**：选了「我按月付 ¥68/月」之后，只要区间里用过两个模型，

- **兜底估算按每条调用自己的时间取别名**：以前带时间区间的别名按"现在"判定，

- **保存配置不再打死远程价格表的 24 小时刷新**：以前保存任意一次设置就会清掉定时器、且不再重建，
